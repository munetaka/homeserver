# 2026-08-17: 新検針期間のコスト欠落と、8月請求分の支援値引き二重計上

## 概要

検針日(8/10)を過ぎても検針期間別パネルに新期間(請求月 2026-09)の棒が現れない、
というユーザーの指摘から調査。直接原因は tariff.py の燃料費調整テーブルが 2026-08 まで
しか登録されておらず、8/10 以降の日次コストが**警告のみでサイレントにスキップ**されて
いたこと。さらに調査の過程で、既登録の 2026-08 の単価が**国の支援値引き込み(反映後)の
値**になっており、SUBSIDY_YEN と**二重計上**されていたことが発覚した。

## 根本原因

1. **単価未登録によるサイレント欠落**: `build_cost_lines` は単価テーブルにない月を
   「警告して日次をスキップ」する設計(意図された安全側挙動)。しかし警告は
   cost-update の journal にしか出ないため、毎月10日の検針期間切り替わり時に
   単価が未登録だと、誰も気づかないままコスト系列が止まる。
2. **反映前/反映後の取り違え**: TEPCO の公式一覧・お知らせには「電気・ガス料金支援
   反映前」と「反映後」の2つの単価が並ぶ。支援値引きは SUBSIDY_YEN で別管理して
   いるのに、2026-08 の燃調として反映後(−10.27 = −6.77 − 3.50)を登録していた。
   両者の検算(反映前 + 支援 = 反映後、前月比)をしていなかった。

## 影響

- 2026-08-10〜08-16 の cost_day_yen / 進行中期間の cost_period_yen が**未書き込み**
  (パネルの棒が出ない。kWh 系メトリクスは無傷)
- 検針期間 2026-08(07-10〜08-09)の cost_day_yen(buy/savings)と cost_period_yen が
  **3.50円/kWh 過小**(限界単価 21.13 → 正 24.63円/kWh。請求見込みは買電量×3.5円分低い)

## 対応

1. tariff.py: 2026-08 を反映前の −6.77 に修正、2026-09(反映前 −6.46)を追加。
   出典は TEPCO 公式の月別お知らせページ(9月分・8月分)で、反映前+支援=反映後と
   前月比の両方で検算済み
2. 回帰テスト: 「燃調(反映前) + 支援値引き = TEPCO 公表の反映後単価」の一致を
   固定値で検証するテストを追加(反映後を入れると必ず落ちる)
3. `scripts/health-check.sh` に**コスト系列の鮮度チェック**を追加(60時間超で
   cost-update の journal 確認を促す)。サイレント欠落の検知手段
4. デプロイ後に `el cost-update --since 2026-07-10` で影響期間を全再計算
   (VM は dedup 有効のため同タイムスタンプの上書きで収束する)

## 教訓

- **「警告してスキップ」は、その警告を人が見る仕組みとセットでないと事故になる**。
  定期ジョブのサイレントな部分失敗はヘルスチェックに鮮度として現れるようにする
- 公式ソースから単価等を転記するときは、**同じページ内の冗長な情報(合計列・前月比)で
  検算**してから登録する。反映前/反映後のように紛らわしい2値が並ぶ表は特に危ない
- 毎月10日すぎに燃料費調整単価の追加が必要(TEPCO の翌月分発表は前月末ごろ)。
  tariff.py のコメントと本記録を参照(→ 2026-10-28 に自動化。下記続報)

## 続報 (2026-10-28): 同じ原因で再発 → 燃調の自動取得を導入

### 何が起きたか

検針期間別パネルの棒が 2026-08 請求分(〜9/9)で止まっている、とユーザーが指摘。
原因は前回と同一で、`FUEL_ADJUSTMENT_YEN` が 2026-09 までしか登録されておらず、
9/10 以降(請求月 2026-10・2026-11)の cost 系列が約7週間**未書き込み**だった
(kWh 系は無傷。導出データなので再計算で完全復旧)。前回の対策3(health-check の
コスト鮮度チェック)は**ヘルスチェックを誰も実行しなければ発火しない**ため効かなかった。

### 対応

1. 2026-10(反映前 −5.80、支援 −3.50 は最終月)・2026-11(−5.33、支援なし)を登録し、
   `el cost-update --since 2026-09-10` で再計算(commit `b7c64bc`)
2. **再発防止 = 手動登録をやめる**: `el tariff-fetch` + `tariff-fetch.timer`(週次)が
   TEPCO の燃調一覧を取得し、未登録の新しい請求月を overlay
   (`/opt/homeserver/var/fuel_adjustment.json`)へ自動追記する(commit `a5fc553` 以降)。
   Pi 単体で完結し、Mac やエージェントのアカウントに依存しない
3. **二重計上の構造的な封じ込め**: 一覧ページの掲載値は支援**反映後**の適用値。overlay は
   この1値だけを持ち、内訳(fuel / subsidy)は SUBSIDY_YEN 登録月のみ逆算する。請求計算は
   fuel+subsidy の和しか使わないため、反映前/反映後の取り違えが起きる余地がない。
   さらに毎週、**定数登録値(反映前+支援)と公表値を照合**するので手入力ミスも検出される
4. **人が見る場所に出す**: 前回の教訓「警告は人が見る仕組みとセットで」を踏まえ、
   電力ダッシュボードに「燃調単価テーブル」と「燃調自動取得」stat(取得/照合/充足)を追加。
   取得が壊れても、請求月が未登録になった時点で充足が赤になる

### 教訓

- **定期作業を手順書に書くのは対策にならない**。2回目が起きたら自動化するか、
  少なくとも毎日見る画面に期限切れを出す
- 外部データの自動取り込みは「検証に通らなければ書かない」+「失敗が画面に出る」の
  2点セットで、誤値よりも停止(=可視化された欠落)を選ぶ
